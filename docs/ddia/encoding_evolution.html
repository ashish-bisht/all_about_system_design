The Core Problem

🍕

Swiggy Rolling Upgrade — What goes wrong?

Swiggy has 10 servers. Product team added address field. Servers 1-3 are updated, 4-10 still running old code.

Server 1 (NEW)
→
Saves order WITH address
Server 5 (OLD)
→
Reads record, updates it
→
address DELETED! 😱
⚠️ Key Insight Old code must PRESERVE unknown fields — even if it can't understand them. Ignoring ≠ Deleting.

← Backward Compatibility

New code reads OLD data

Naya server deploy hua, purana data database mein pada hai — naya code usse padhne mein capable hona chahiye.

Usually easy — tum khud new code likhte ho!

→ Forward Compatibility

Old code reads NEW data

Purana server abhi chal raha hai, naya format ka data aa gaya — usse gracefully ignore karna padega.

Tricky — old code nahi jaanta future fields!

💡 Data Outlives Code Tera code har 2 hafte deploy hota hai. But DB mein 5 saal purana data pada hai. Naya code HAMESHA purana data padhne ke liye ready hona chahiye.

Encoding Formats — Comparison

Format Schema? Size (example) Human Readable? Compat Mechanism Use When
JSON / XML Optional 81 bytes ✓ Yes Field names (fragile) Public APIs
Protocol Buffers Required 33 bytes ✗ No Field tags (numbers) Internal Services
Avro Required 32 bytes ✗ No Writer + Reader schema Hadoop / Kafka
MessagePack No 66 bytes ✗ No Field names (still included) Niche binary JSON
03

Protocol Buffers — Deep Dive

🏷️

Field Tags, Not Names

Network pe "userName" string nahi jaata — sirf tag number 1 jaata hai. Field rename karo? Safe. Tag change karo? 💥 Sab data corrupt.

33 bytes vs 81 bytes JSON
➕

Adding a Field Safely

Naya field add karo with a NEW tag number. Old code: unknown tag dekha → skip. New code: field missing in old data → default value fill in.

Both directions safe ✓
🚫

Never Reuse Tags

Ek baar tag 3 use kiya, fir woh field remove ki — tag 3 reserve karo schema mein. Kabhi reuse mat karo.

Hard Rule
⚡

Protobuf Kyun Use Nahi Hota Everywhere?

Binary = not human readable (debug mushkil). Schema likhna padta hai (slow iteration). Browser directly support nahi karta.

Internal only
💻

Swiggy Order — Protobuf Schema Evolution

V1 schema — original:

// V1 — original message Order { int64 user_id = 1; string item = 2; int64 price = 3; }

V2 — address field add kiya:

// V2 — address added safely message Order { int64 user_id = 1; string item = 2; int64 price = 3; string address = 4; // ← new tag, safe! }
✅ Result Old server (knows 1,2,3) reads new data → sees tag 4 → ignores it → safe!
New server reads old data → address missing → fills "" default → safe!
04

Apache Avro — The Interesting One

🔮

Avro Magic — No Tags, No Field Names in Binary!

Avro binary mein sirf values hain — koi field name, koi tag number nahi. 32 bytes — sabse compact!

// Wire pe yeh jaata hai: [101]["Biryani"][250] // Koi "user_id", koi tag — sirf values!

But agar koi identity nahi hai toh decode kaise hoga? Avro uses two schemas:

Writer's Schema

Jis app ne data encode kiya, uska schema. Data ke saath store/send hota hai (version number ke roop mein).

Reader's Schema

Jo app data decode kar raha hai, uska schema. Avro dono ko compare karke fields ko name se match karta hai.

🔑 Key Difference from Protobuf Protobuf = fields matched by TAG NUMBER
Avro = fields matched by FIELD NAME

Avro mein field rename karna possible hai (aliases se) — Protobuf mein nahi!
✅

Safe in Avro

Default value wala field add/remove karna. Field rename (using aliases). Datatype change (if Avro can convert).

Forward + Backward safe
💥

Breaks Compatibility

Default value ke bina field add karna. Default value ke bina field remove karna. null use karna without union type.

Avoid these!
🏭

Avro Best For

Dynamically generated schemas! DB schema se automatically Avro schema generate karo. Protobuf mein yeh manually karna padta — Avro mein auto!

Hadoop, Kafka, Analytics

3 Modes of Dataflow

🗄️

Mode 1 — Through Databases

New Code
writes→
Database
→reads
Old Code
→
BOTH compatibilities needed!

DB mein ek saath old aur new code access karta hai. Isliye both backward AND forward compatibility chahiye — unlike REST where servers update first.

Remember: Data Outlives Code 5 saal purana data DB mein pada rahega. Code changes — data stays.
🌐

Mode 2 — REST & RPC (Services)

Client
—request→
Server (updated first)
←response—
Client (updated later)

Servers pehle update hote hain, clients baad mein. Isliye:

Request — Backward Compat

Old client sends request → new server reads it. Server must handle old format requests.

Response — Forward Compat

New server sends response → old client reads it. Old client must ignore new fields gracefully.

RPC vs REST RPC: Network call ko local function jaisa dikhata hai → Fundamentally WRONG!
Network can timeout, fail, retry (causing duplicates), be slow.
REST: Openly treats it as network transfer → Honest approach ✓

Sync + Simple → REST + JSON

06

🎤 FANG Interview Q&A

"How would your microservices communicate with each other?"
Internal services mein gRPC + Protobuf use karunga — compact, fast, type-safe. Public APIs ke liye REST + JSON — browser friendly, debug easy. Async workflows ke liye Kafka + Avro — decoupled, buffered, schema-evolved.
"How do you handle schema changes without downtime?"
Rolling upgrades use karunga. Encoding format mein backward + forward compat ensure karunga. Protobuf mein naye fields naye tags se add karunga, purane tags kabhi reuse nahi karunga. Database mein — data outlives code — isliye schema migrations carefully likhna hoga with default values.
"Protobuf vs Avro — when would you pick which?"
Protobuf: static schema, gRPC services, internal microservices. Field tags se compat maintain karna easy hai. Avro: dynamic/generated schemas, Kafka, Hadoop. Avro friendlier hai jab schema automatically DB se generate hoti ho — no manual tag assignment.
"What's the difference between backward and forward compatibility?"
Backward: new code reads old data (new server, old DB records). Forward: old code reads new data (old server running during rolling upgrade, gets new format data). Both needed in DB context. For REST — backward on request, forward on response.
