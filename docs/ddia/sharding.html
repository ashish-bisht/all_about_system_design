01

Sharding Kya Hai?

🗄️
Single Node
Sab data ek hi machine pe. Simple hai, lekin scale nahi hota.
⚡
Overflow!
Data ya writes itne zyada ho gaye ki ek machine handle na kar sake.
✂️
Shard Karo
Data ko pieces mein todo. Har shard ek alag node pe.
🔁
+ Replication
Har shard ke copies bhi rakho — fault tolerance ke liye.
Kab Use Karein

Sharding vs Replication

  • Read throughput problem → Replication use karo
  • Write throughput problem → Sharding use karo
  • Data volume too large → Sharding use karo
  • Fault tolerance chahiye → Replication use karo
  • Production mein dono saath use hote hain
Dhyan Rakho

Sharding Ke Nuksan

  • Complexity badh jaati hai
  • Partition key choose karna mushkil
  • Secondary indexes complicated ho jaate hain
  • Distributed transactions slow hote hain
  • Cross-shard joins mushkil hain
02

Sharding Strategies

Strategy Kaise Kaam Karta Hai Faida Nuksan Used In
Key Range Keys sort order mein range-wise assign Range queries efficient Hot shard risk (e.g. timestamp) HBase, MongoDB, Bigtable
Hash of Key key ka hash nikalo, phir assign karo Even distribution Range queries inefficient MongoDB, Cassandra
Hash + Range Partition key pe hash, baki pe sort Best of both worlds Slightly complex DynamoDB, YugabyteDB
Consistent Hashing Hash ring pe keys map karo Minimal data movement on rebalance Uneven distribution possible Cassandra, ScyllaDB, Riak
Fixed Shards Pehle se zyada shards banao, nodes pe assign karo Easy rebalancing Wrong initial count = expensive resharding Elasticsearch, Couchbase, Riak
Example

Key Range — Encyclopedia Analogy

Jaise encyclopedia mein Volume 1 = A-B, Volume 2 = C-D... har volume ek shard hai. Boundaries evenly spaced nahi hoti — data distribution ke hisaab se adjust hoti hain.


⚠️ Timestamp Problem: Agar key timestamp hai, to saare writes current month ke shard pe jaayenge — hot shard ban jaayega.


✅ Fix: Key ko sensor_id + timestamp banao. Writes sab sensors mein spread ho jaayenge.

Hash Sharding

Mod N Problem

hash(key) % N simple hai lekin problem yeh hai ki jab N change hota hai (node add/remove), almost saare keys move hote hain naye nodes pe.


✅ Fix — Fixed Shards: 10 nodes hain to 1000 shards banao. Node add karne pe sirf kuch shards move honge. Shards ki count change nahi hoti, sirf assignment change hoti hai.

03

Hot Spots & Skew

Problem

Koi ek key bahut zyada load le rahi hai. Jaise celebrity ka post viral ho gaya — uss user ID pe lakho reads/writes aa rahe hain. Hot key = hot shard = bottleneck.

Write Fix

Hot key ke aage random 2 digits add karo. user_123 → user_123_47, user_123_12... 100 keys ban jaate hain, writes 100 shards mein spread. Lekin reads ko sab 100 se combine karna padega.

Cloud Solution

Amazon ka Adaptive Capacity / Heat Management — automatically detect karta hai hot shards aur unhe split karta hai ya rebalance karta hai without manual intervention.

04

Rebalancing

Automatic

Auto Rebalancing

  • Shard size threshold cross kare to split (HBase default: 10GB)
  • Write throughput too high → split
  • DynamoDB: minutes mein scale in/out
  • Risk: Slow node ko dead samajh ke rebalance shuru kar do → cascading failure
  • Risk: Split karna expensive hai — already overloaded shard pe aur load
Manual

Manual Rebalancing

  • Admin decide karta hai kab split/move karein
  • Couchbase/Riak: auto suggest karo, human approve kare
  • Predictable events ke liye useful — Cyber Monday, World Cup ticket sale
  • Slower than auto lekin safer
  • Vitess (MySQL sharding): manual key-range boundaries
Key Insight

Shards Manage Karne Ke 2 Options

Jab data distributed ho, ek coordinator chahiye hoga — shard-to-node mapping track karne ke liye.

Option 1 — External: ZooKeeper / etcd use karo (HBase, SolrCloud, Kubernetes). Battle-tested, lekin ek aur moving part.

Option 2 — Built-in: Raft protocol andar hi implement karo (Kafka, TiDB, YugabyteDB, ScyllaDB). Ek kam dependency.

Option 3 — Gossip: No central coordinator, nodes aapas mein baat karte hain (Riak). Weak consistency, possible split brain. Leaderless DBs ke liye okay.

05

Request Routing

Problem: Key X ke liye konse node pe jaana hai? Yeh routing problem hai — service discovery ka distributed DB version.

1
Any Node → Forward
Client kisi bhi node pe jaaye. Wo node check kare — agar uske paas hai to serve kare, nahi to sahi node pe forward kare.

Used: Riak, Cassandra
2
Routing Tier
Ek dedicated routing layer jo shard mapping jaanti hai. Client pehle routing tier pe jaata hai, jo sahi node pe forward karta hai.

Used: MongoDB (mongos), many cloud DBs
3
Client Aware
Client khud jaanta hai ki kaunsa key kahan hai. Seedha sahi node pe connect karta hai. Sab se efficient lekin client ko update rakhna padta hai.

Used: Cassandra drivers
06

Secondary Indexes & Sharding

Problem: Sharding partition key pe based hoti hai. Lekin secondary indexes (color, make, user_id) kahan rakho?

🏠 Local Secondary Index

Har shard apna index khud maintain karta hai — sirf apne records ka.

Write Speed Fast ✓
Read (secondary) Slow — all shards ✗
Pattern Scatter-Gather
Used In MongoDB, Cassandra, Elasticsearch
Example: Red cars dhundho → har shard pe query bhejo → results combine karo. Tail latency amplification risk.

🌍 Global Secondary Index

Index khud alag shard pe hota hai — indexed value ke hisaab se sharded.

Write Speed Slow — multiple shards ✗
Read (secondary) Fast — 1 shard ✓
Consistency Often async (stale reads possible)
Used In CockroachDB, TiDB, DynamoDB
Example: color:red shard pe jaao, wahan se IDs lo, phir primary key shards pe jaao. Write complexity zyada.

Multitenancy & Data Residency

🇮🇳
India Shard
DPDPA
Indian users ka data India mein hi rahega. Mumbai/Pune data center.
🇪🇺
Europe Shard
GDPR
EU citizens ka data EU mein rahega. Right to erasure — sirf is shard ko delete karo.
🇺🇸
US Shard
CCPA
US users ka data US mein rahega. Schema same, data alag.
Faida 1

Resource Isolation

Ek tenant ka heavy operation doosre tenants ko affect nahi karta agar wo alag shard pe hain.

Faida 2

Cell-Based Architecture

Services + storage ko ek cell mein group karo. Ek cell mein fault aaye to baaki cells safe rahti hain.

Challenge

User Migration

Agar user India se Europe shift ho jaaye — uska data ek shard se doosre mein move karna padega. Non-trivial operation!

09

FANG Interview Q&A

  • Sharding aur Replication mein kya fark hai?
    Replication — same data multiple nodes pe store karo. Read scaling aur fault tolerance ke liye.

    Sharding — alag data alag nodes pe. Write scaling aur huge data volume ke liye.

    Production mein dono saath use hote hain — har shard ki replicas hoti hain.
  • Hot Spot kya hota hai aur kaise fix karein?
    Jab ek shard pe disproportionately high load aa jaaye — ya to data volume zyada hai ya request rate zyada hai. Celebrity post viral hona iska real example hai.

    Fix 1: Hot key ke saath random suffix add karo — user_123_47. Writes 100 keys mein spread honge. Reads ko sab 100 se combine karna padega.

    Fix 2: Cloud solutions — Amazon Adaptive Capacity automatically hot shards ko split/rebalance karta hai.

    Fix 3: Hot key ko dedicated shard/machine dedo.
  • Consistent Hashing kya hai?
    Ek hashing algorithm jo 2 properties guarantee karta hai:

    1. Har shard pe roughly equal keys mapped hote hain.
    2. Jab shard count change ho, minimum keys move karein.

    Yeh "consistent" word consistency (ACID/replica) se related nahi hai — yahan consistent matlab hai ki key ko usi shard mein rehna chahiye jab bhi possible ho.

    Variants: Rendezvous hashing (highest random weight), Jump consistent hashing, Cassandra's vnodes.
  • Local vs Global Secondary Index — kab kaunsa choose karein?
    Local index choose karo jab: Write throughput zyada important hai. Reads mein thodi latency acceptable hai. MongoDB, Cassandra use cases.

    Global index choose karo jab: Read throughput zyada important hai (reads > writes). Postings lists badi nahi honi chahiye. Staleness acceptable hai (async updates). DynamoDB, CockroachDB use cases.

    Yad rakho: local = fast write, slow read (scatter-gather). Global = slow write, fast read (single shard postings list).
  • Design a global app with data residency requirements (GDPR, DPDPA)?
    Approach — Geo-Based Sharding:

    1. Shard by region/country. India users → India shard, EU users → EU shard, US users → US shard.
    2. Schema same hogi sab jagah, sirf data alag.
    3. GDPR right to erasure → sirf EU shard pe delete operation — doosre tenants unaffected.
    4. Cell-based architecture use karo — har region ek self-contained cell. Ek cell fail ho to baaki safe.

    Challenge: User migration (India se EU shift) — non-trivial shard migration operation.
    Challenge: Cross-region features (global leaderboard, etc.) — cross-shard joins needed.
  • Auto vs Manual Rebalancing — kaunsa prefer karein?
    Auto rebalancing pros: Koi manual work nahi, DynamoDB-style cloud DBs minutes mein scale in/out.

    Auto rebalancing risks: Slow node ko dead samajh ke rebalance shuru karo → cascading failure. Already overloaded shard split karna aur load badha deta hai.

    Manual pros: Predictable events ke liye preemptive rebalancing (Cyber Monday, World Cup).

    Best of both — Middle ground: Couchbase/Riak style — auto suggest karo, human approve kare. Production mein yahi safer hai.
  • Kab sharding avoid karni chahiye?
    Jab tak ek single machine data aur write throughput handle kar sake — sharding avoid karo.

    Single machine aajkal bahut powerful hoti hai. Sharding add karne se:
    — Partition key choose karni padti hai
    — Schema change mushkil ho jaata hai
    — Cross-shard transactions slow hote hain
    — Secondary indexes complicated ho jaate hain

    Rule of thumb: Read scaling chahiye? Replication use karo. Write scaling / huge data? Tab sharding.
  • ZooKeeper kya karta hai sharding mein?
    ZooKeeper ek coordination service hai jo shard-to-node mapping track karta hai.

    — Har node apne aap ko ZooKeeper mein register karta hai
    — ZooKeeper authoritative mapping maintain karta hai
    — Routing tier / clients ZooKeeper subscribe karte hain changes ke liye
    — Shard move ho to ZooKeeper routing tier ko notify karta hai

    Consensus algorithm use karta hai (Paxos/ZAB) — fault tolerant, split brain se protection.

    Alternative: etcd (Kubernetes), Raft built-in (Kafka, TiDB), Gossip (Riak — weak).
