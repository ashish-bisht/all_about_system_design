Isolation Levels

MUST KNOW
Level 1 — Read Committed
DEFAULT in PostgreSQL, Oracle
✅ PREVENTS
Dirty Reads
Dirty Writes
❌ STILL POSSIBLE
Read Skew
Lost Updates
Write Skew
Flipkart Price Update
Seller: UPDATE price = ₹1299 ← not committed yet Tu: SELECT price → ₹999 ← purana committed value ✅ Seller: ROLLBACK ← tu ne kabhi ₹1299 dekha hi nahi ✅
Level 2 — Snapshot Isolation (MVCC)
PostgreSQL Repeatable Read
✅ PREVENTS
Dirty Reads
Dirty Writes
Read Skew
❌ STILL POSSIBLE
Write Skew
Lost Updates (sometimes)
MVCC — Multi Version Concurrency Control
/* Har row ke multiple versions */ | price | inserted_by | deleted_by | | ₹999 | txn_10 | txn_15 | ← purana | ₹1299 | txn_15 | null | ← naya Tu txn_12 hai → txn_15 > txn_12 → ₹1299 nahi dikhega → ₹999 dikhega ✅ time freeze!
Key: Readers never block writers. Writers never block readers. ✅
Level 3 — Serializable
GOLD STANDARD
✅ PREVENTS
Everything ✅
Dirty reads, Write skew,
Phantoms, Lost updates
⚠️ TRADEOFF
Performance cost
More aborts possible
3 Implementations:
1. Serial Execution
2. 2PL (Two Phase Locking)
3. SSI (Serializable Snapshot Isolation) ⭐
Use when:
Banks 🏦
Hospitals 🏥
Financial systems 💰
Quick Pick Guide
Normal e-commerce reads/writes → Read Committed (fast) Analytics, backups, reports → Snapshot Isolation (consistent view) Banks, hospitals, payments → Serializable (safe, slower)

Lost Update

MUST KNOW
Flipkart Flash Sale — 1 iPhone, 10 Lakh Users
THE PROBLEM — Read-Modify-Write cycle User A: SELECT stock → 1 User B: SELECT stock → 1 ← gap mein dono ne padha User A: UPDATE stock = 0 ✅ User B: UPDATE stock = 0 ✅ ← A ka update LOST! 😱 Result: 2 orders, 1 iPhone, stock = 0 (not -1 even!)
4 Fixes:
Fix 1 — Atomic Operation ⭐
UPDATE products SET stock = stock - 1 WHERE id = 1; ← Gap hi khatam, DB calculate karta hai ← Best for: counters, likes, stock
SIMPLEST
Fix 2 — SELECT FOR UPDATE
BEGIN; SELECT * FROM products WHERE id = 1 FOR UPDATE; ← row lock! -- complex logic yahan UPDATE products SET stock = 0; COMMIT;
COMPLEX LOGIC
Fix 3 — Auto Detection (PostgreSQL)
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ; ← DB khud detect karta hai ← Conflict? Auto ABORT + retry ← No extra code needed ✅ ← MySQL InnoDB mein kaam nahi karta ❌
POSTGRES ONLY
Fix 4 — Compare and Set (CAS)
UPDATE products SET description = 'new text' WHERE id = 1 AND description = 'old text'; ← Sirf tab update karo jab value wahi ho jo tune padhi thi ← MVCC ke saath careful! ⚠️
NO-TXN DBs
⚡ FANG Interview tip: "Lost update prevent karna hai?" → Pehle atomic op try karo. Complex logic hai? → SELECT FOR UPDATE. PostgreSQL hai? → Isolation level set karo.

Write Skew vs Lost Update

MUST KNOW
Lost Update
Do transactions same row update karte hain.

Ek ka update overwrite ho jaata hai.
A: UPDATE stock → 0 B: UPDATE stock → 0 ← A's update gone
Write Skew ← Harder!
Do transactions alag rows update karte hain.

Combined effect invariant violate karta hai.
A: UPDATE raju → offline B: UPDATE shyamu → offline ← 0 delivery boys! 😱
Flipkart Delivery System — Write Skew
Initial State
Raju: available=true | Shyamu: available=true
Rule: minimum 1 delivery boy online hona chahiye
Both Transactions Start
Raju ki transaction: COUNT → 2 ✅ "2 > 1, main ja sakta hun"
Shyamu ki transaction: COUNT → 2 ✅ "2 > 1, main ja sakta hun"
← Dono ne same snapshot dekha
Both Commit
Raju: UPDATE available=false → committed ✅
Shyamu: UPDATE available=false → committed ✅
Result: 0 delivery boys! Rule violated! 😱
Fix for Write Skew:
Fix 1 — SELECT FOR UPDATE
BEGIN; SELECT * FROM delivery_boys WHERE city='Mumbai' AND available=true FOR UPDATE; ← dono rows lock! -- count check karo -- agar > 1, tab hi proceed UPDATE delivery_boys SET available=false WHERE id=1; COMMIT;
Works when rows EXIST
Fix 2 — Serializable Isolation
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE; ← DB conflict detect karega ← Ek transaction abort hogi ← Retry karega → sahi count milega ← Best option always ✅
ALWAYS WORKS
Phantom — Write Skew ka Extreme Version
Flipkart Slot Booking — Phantom Problem
/* Rule: ek slot mein max 2 orders */ Manager A: SELECT COUNT(*) WHERE slot='9pm' → 1 Manager B: SELECT COUNT(*) WHERE slot='9pm' → 1 Manager A: INSERT order_B into 9pm slot ✅ Manager B: INSERT order_C into 9pm slot ✅ Result: 3 orders in one slot! 😱 /* SELECT FOR UPDATE kyun fail hoga? */ Sirf ORDER_A row thi → wahi lock hui ORDER_C exist hi nahi karti thi → kisko lock karte? 🤷 Yahi hai PHANTOM
🔑 Key difference: Write Skew → existing rows update. Phantom → new rows insert hoti hain jo condition tod deti hain. Dono ke liye best fix = Serializable Isolation.

Two Phase Commit (2PC)

MUST KNOW
Flipkart Order — 3 Cities, 3 Databases
Orders DB → Mumbai Inventory DB → Delhi Payment DB → Bangalore Problem without 2PC: Orders DB: INSERT order ✅ committed Inventory DB: UPDATE stock ✅ committed Payment DB: INSERT payment 💥 CRASH ← 2 committed, 1 not → inconsistency!
Phase 1 — Prepare
Coordinator → Orders DB: "Commit kar sakta hai?" → YES ✅ Coordinator → Inventory DB: "Commit kar sakta hai?" → YES ✅ Coordinator → Payment DB: "Commit kar sakta hai?" → YES ✅ ← YES matlab: "Data disk pe likh liya, promise kiya, ab rollback nahi" ← Participant ka point of no return!
Phase 2 — Commit
Sab ne YES bola → Coordinator commits: Coordinator → Orders DB: "COMMIT!" ✅ Coordinator → Inventory DB: "COMMIT!" ✅ Coordinator → Payment DB: "COMMIT!" ✅ Sab consistent! ✅ Koi bhi NO bolta → Coordinator aborts sab: Coordinator → Orders DB: "ABORT!" Coordinator → Inventory DB: "ABORT!" Coordinator → Payment DB: "ABORT!"
⚠️ COORDINATOR CRASH — Biggest Problem
Phase 1 done → sab ne YES bola Coordinator ne Orders DB ko COMMIT bheja ✅ Coordinator CRASH 💥 Inventory DB aur Payment DB: "Haan bol chuke hain... ab kya?" "Commit karein? Abort karein?" → "IN DOUBT" state 😱 → Rows LOCKED — koi access nahi kar sakta Fix: Coordinator decision pehle DISK PE LIKHTA HAI Recovery pe: log padho → retry karo ✅
2PC Works Well
✅ Database-internal txns
✅ Same software on all nodes
✅ CockroachDB, TiDB, Spanner
✅ Coordinator replicated
2PC Problems
❌ Blocking protocol
❌ Coordinator = single point of failure
❌ XA transactions — lowest common denominator
❌ Locks held while in doubt
💡 2PC ka two points of no return: (1) Participant YES bolta hai → ab rollback nahi. (2) Coordinator commits → irrevocable decision.

Quiz — FANG Style

TEST YOURSELF
Q1. Instagram pe 2 log ek saath same post ko like karte hain. likes counter ek baar hi badha. Yeh kaun sa problem hai?
✅ Lost Update! Do transactions ne same row padhi (likes count), modify ki, wapas likhi. Ek ka update kho gaya. Fix: atomic operation — UPDATE SET likes = likes + 1
Q2. Flipkart Finance dashboard mein total orders aur total revenue numbers match nahi kar rahe — ek 10:00 AM ka data dikha raha hai, doosra 10:00:03 AM ka. Kaun sa anomaly hai?
✅ Read Skew! Same transaction ne different points in time ka data dekha. Fix: Snapshot Isolation — MVCC use karo, poora audit ek consistent snapshot se hoga.
Q3. Hospital system mein rule hai — minimum 1 doctor on call. Raju aur Priya dono ek saath off jaate hain. 0 doctors. Kaun sa problem?
✅ Write Skew! Dono ne alag rows update ki — lekin combined effect ne invariant violate kiya. Fix: SELECT FOR UPDATE ya Serializable Isolation.
Q4. 2PC mein coordinator ne sab participants se YES liya. Phir coordinator crash ho gaya commit request bhejne se pehle. Participants ka kya hoga?
✅ In Doubt! Participants kuch nahi kar sakte — sirf coordinator ka wait. Rows locked rahenge. Coordinator recover hone pe log se decision padh ke retry karega.
Q5. Ek coupon sirf 3 baar use ho sakta hai. 2 users simultaneously check karte hain "2 baar hua hai" aur dono use karte hain. 4 baar use ho gaya. Kaun sa problem?
✅ Phantom! Dono ne check kiya "rows exist nahi karti" — dono ne insert ki. Future rows ne condition tod di. SELECT FOR UPDATE kaam nahi karta kyunki lock karne ki rows thi hi nahi. Fix: Serializable Isolation.
