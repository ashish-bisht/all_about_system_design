Access Patterns &

⚠️ "Write Heavy" ko pehle split karo

Type A

Mostly UPDATEs

Same data baar baar change hoti hai. Price change, inventory count, user status.

-- 1 write, done ✓
UPDATE products
SET price = 999
WHERE id = 42;
Type B

Mostly INSERTs

Naya data stream hota rehta hai. Logs, events, transactions, sensor data.

-- Har second naya row
INSERT INTO sensor_events
VALUES (ts, device_id, val);
-- 10,000 rows/sec
The Real Problem: Write Amplification
Ek logical write → kitni physical disk writes? Index har table pe update hota hai.

📊 Scenario → Strategy Map

📖
Read Heavy
Denormalize + Cache
80%+ reads. JOINs at scale are expensive. Pre-compute what you'll read.
→ Store data as you READ it, not as it logically exists
Social feed Product catalog Dashboard
✏️
Write Heavy — UPDATEs
Normalize
Same data changes frequently. One source of truth → one update. No write amplification.
→ Single row update propagates everywhere via JOIN
Inventory Pricing User profile
➕
Write Heavy — INSERTs
Append-Only + Few Indexes
Naya data stream hota hai. Primary focus: minimal indexes + partitioning. Normalize/denorm secondary hai — normalize se row size smaller hoti hai (better cache), but per-insert multi-table writes + FK checks throughput hurt karte hain.
→ Append-only fact table + partitioning. Dimension lookups async/late-binding.
IoT sensors Event logs Analytics
⚖️
Mixed — Production Reality
CQRS + Hybrid Architecture
Write path aur Read path alag karo. DB normalize karo (source of truth). Reads ke liye denormalized views async mein sync karo via Read Replicas / Redis / Elasticsearch.
→ Write → Normalized DB → async sync → Read Store (Redis/ES/Replica)
⚠️ Trade-off: Eventual Consistency — write ke baad read pe thodi der stale data aa sakta hai
E-commerce SaaS Search-heavy apps
🔥
Extreme Write Throughput
Tune First, Then Engine Change
Pehle try karo: partitioning + batch inserts + minimize indexes + async commit. Agar phir bhi nahi hua toh LSM-tree engine consider karo.
→ Tune existing DB first → then Cassandra/ScyllaDB/RocksDB
💡 Why LSM wins here: B-Tree = random IO on update (in-place). LSM = sequential append to memtable → flush. No random disk seeks.

🔍 "Locking" ≠ Sirf Read-Write Block
Modern DBs (PostgreSQL, MySQL InnoDB, Oracle) MVCC use karte hain — reads writers ko block nahi karte. Real contention alag jagah hoti hai:
❌ Aam Assumption

"Write heavy mein reads block ho jaate hain, isliye slow hai"

✓ MVCC Reality

Readers never block writers. Actual bottleneck: index hot spots + buffer contention + WAL/write-ahead log pressure.

Index Hot Spot

Monotonic keys (auto-increment IDs) → B-tree ke right-hand leaf pe sab inserts pile up → buffer contention badh jaata hai

✓ Fix

Hash partitioning ya UUID keys se inserts distribute hote hain across B-tree. Hot block problem solve.

WAL Pressure

Bulk inserts mein Write-Ahead Log writes alag bottleneck hain — normalize/denorm se iska koi lena dena nahi.

✓ Fix

Batch inserts + async commit se throughput kaafi improve hoti hai engine switch karne se pehle.

⚠️ Common Myths Busted
Jo log galat bolte hain vs reality
❌ Myth

"Write heavy mein hamesha normalize karo"

✓ Reality

Sirf UPDATE-heavy mein clearly helpful. INSERT-heavy mein normalize/denorm secondary hai — focus hona chahiye minimal indexes + partitioning pe.

❌ Myth

"Normalize karo toh indexes ka problem solve ho jaata hai"

✓ Reality

Normalize se har table ka index alag update hota hai. Problem solve nahi, distribute hoti hai.

❌ Myth

"Denormalize karo toh writes expensive ho jaati hain"

✓ Reality

INSERT-heavy workload mein denormalized bhi theek hai. UPDATEs ke saath problematic hai.

❌ Myth

"Ek DB engine sab ke liye kaam karega"

✓ Reality

B-tree (PostgreSQL/Oracle) reads ke liye great. LSM-tree (Cassandra) extreme writes ke liye better.

👑

The Real Mental Model

Pehle pucho: write ka type kya hai?
UPDATE → Normalize. INSERT-stream → Append-only + partition.
Dono hain → CQRS: Normalize writes, async denormalize reads.
Async read store ka cost = Eventual Consistency. Acceptable hai ya nahi — product decision hai, engineering nahi.
