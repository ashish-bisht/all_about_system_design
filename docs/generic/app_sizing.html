01
CPU-bound vs I/O-bound — Fundamental Distinction

Ye decision sabse pehle karna padta hai. Teri app kya karti hai zyada?

I/O Bound
Wait
DB calls, network, file reads.
CPU idle rehta hai wait mein.
→ More workers beneficial
CPU Bound
Compute
ML inference, encryption,
image processing.
→ More cores needed
URL Shortener = Pure I/O bound. DB lookup → redirect.
CPU barely touched. 99% time = waiting for DB response.
02
Python GIL — Why Multiple Workers?

Python ka GIL (Global Interpreter Lock) — ek process ek time pe sirf ek CPU core use kar sakta hai. Chahe 16 cores hon.

# 1 Process = 1 Core at a time (GIL)
# 8 cores available → 7 cores waste agar 1 worker

Solution:
Multiple Workers = Multiple Processes = GIL bypass
Har process apna core use karta hai independently

Workers aapas mein ladte nahi — OS ka scheduler time-slicing se handle karta hai. Jab Worker 1 I/O pe wait kare, Worker 2 core le leta hai.

03
Workers Formula — Aur Iska Sach
Workers = (2 × CPU cores) + 1   ← Gunicorn default formula
⚠️ Ye formula sirf ek starting point hai.
Blindly follow mat karo. Service ki nature pe depend karta hai.

Service type se workers decide karo:

Service Type Workers Strategy Reason
Pure I/O (CRUD, URL shortener) Zyada workers rakh sakte ho CPU idle rehta hai I/O wait mein
CPU Heavy (ML, image processing) Workers = cores ya kam Zyada workers = context switching overhead
Mixed workload Benchmark karo Koi fixed formula nahi

Sahi approach: Load test karo (Locust/k6), workers badhao, RPS measure karo, jahan plateau aaye wahi optimal.

04
OCI Setup — Production Grade

OCI pe deploy karte waqt yaad rakh: 1 OCPU = 2 vCPU

Shape OCPU vCPU RAM Use Case
E4.Flex 2 4 8GB Dev / Staging
E4.Flex 4 8 16GB Production start ✅
E4.Flex 8 16 32GB High traffic

4 OCPU instance pe workers:

Workers = (2 × 8 vCPU) + 1 = 17 workers
Capacity ≈ 17 × 500 RPS = ~8,500 RPS (conservative, I/O bound)
RAM Breakdown (per instance)
17 workers × ~150MB = ~2.5GB
OS + system = ~1GB
DB connection pool = ~500MB
Cache + buffer = ~4GB
Total recommended = 16GB
Little's Law
RPS = Concurrency / Latency(sec)

1000 concurrent, 100ms latency:
RPS = 1000 / 0.1 = 10,000

Reason Explanation
High Availability Ek gaya toh 2 serve karte rehte hain

Spike Buffer Sudden traffic pe headroom 
3 instances × 8,500 RPS = ~25,500 RPS capacity
Required: 10,000 RPS
Safety margin: 2.5x  ✅
⚠
0.5 CPU Production Pe — What Actually Happens
0.5 CPU production pe = OS sirf 50% time deta hai app ko.
Workers: (2 × 0.5) + 1 = 2 workers only.
Spike aaya → CPU throttle → latency shoot up → timeouts → 💀

2 workers matlab sirf 2 requests practically ek time pe. 10 log ek saath aaye toh 8 log queue mein wait karenge. Production mein ye unacceptable hai.

⚡
Bonus: Global State — FastAPI Mein Never
# ❌ WRONG — global user_id, request_id
user_id = None  # global
request_id = None  # global

@app.get("/user")
async def get_user():
    user_id = get_from_token()  # Race condition!
    # Concurrent request aaya → user_id overwrite
    # Ek user ka data doosre ko → Data Breach 💀
# ✅ CORRECT — request scoped
from fastapi import Request

@app.get("/user")
async def get_user(request: Request):
    user_id = request.state.user_id  # Per-request ✅
Multiple workers = multiple processes.
Global state har process mein alag hota hai — shared nahi.
Concurrent requests pe race conditions guaranteed with globals.
