⚡ Latency Hierarchy — Ye Order Yaad Karo

L1 (1ns) → RAM (100ns) → SSD (100μs) → Network-DC (0.5ms) → DB (1-5ms) → HDD (10ms) → Cross-continent (150ms)
Har level pe roughly 10-100× jump hota hai. Interview mein ye order batao, exact numbers matter nahi karte.

Read:Write Ratio 10:1 (common) Most systems are read-heavy
📐

Step 2 — The 5-Step Formula

universal framework

Har system design interview mein ye 5 cheezein estimate karo. Same order, same approach.

① Traffic / QPS

Avg QPS = DAU × (req/user/day) / 86400
Peak QPS = Avg QPS × 5
Pehle DAU assume karo (10M, 100M, 500M). Phir daily actions per user guess karo (1? 5? 20?). Divide by 86400.

② Storage

Daily = (writes/day) × (size per write)
5 Years = Daily × 365 × 5
Typical sizes: URL = 100B, JSON doc = 1-5KB, Image = 500KB, Video = 50MB. Always think about 5-year retention.

③ Bandwidth

Incoming = (writes/sec) × (write size)
Outgoing = (reads/sec) × (read size)
Outgoing usually >> Incoming (read-heavy). Images/videos ka bandwidth bahut zyada hota hai.

④ Memory / Cache

Cache = Daily reads × avg size × 0.2
(80/20 rule: cache 20% hot data)
80% traffic comes from 20% data. Toh 20% hot data cache karo. Redis typically handles 100K+ ops/sec.

⑤ Servers Needed

Servers = Peak QPS / QPS_per_server
(Web server ≈ 10K QPS, DB ≈ 5K QPS)
Rule of thumb: 1 web server handles ~10K simple QPS. DB is bottleneck — usually need sharding at ~5K+ QPS.

⑥ Read:Write Ratio

Read QPS = Total QPS × (R / R+W)
Write QPS = Total QPS × (W / R+W)
URL Shortener = 100:1 read-heavy. Social media = 10:1. Chat = ~1:1. This changes your architecture!

Step 4 — Interview Mein Kaise Bolo?

script template

Ye exact words bol — interviewer ko lagega ki tujhe pata hai kya kar raha hai:

You: "Let me do some quick back-of-envelope estimation before we dive into the design."
You: "Let's assume we have about [X] million DAU. If each user does roughly [Y] actions per day, that gives us [X×Y] million requests daily."
You: "Dividing by 86,400 seconds in a day, our average QPS is about [Z]. With a 5x peak factor, we need to handle around [5Z] QPS."
You: "For storage, each [object] is roughly [size]. At [writes/day], that's [daily storage] per day, or about [5-year storage] over 5 years."
You: "Given the read-heavy nature ([R:W ratio]), we should focus on caching and read replicas."
🎯 Key Insight

Interviewer ko exact number nahi chahiye — they want to see that you CAN reason about scale. Round aggressively. 86,400 ≈ 100K is totally fine.

🧠

Step 5 — Numbers Se Design Decisions Kaise Nikalein?

the real skill

Estimation sirf numbers ke liye nahi hai — ye tere architecture choices drive karta hai:

High Read:Write (>10:1) → Cache Heavy

Read-heavy = aggressive caching (Redis/Memcached). Multiple read replicas. CDN for static content. 80/20 rule se hot data cache karo.

Billions of Records → Sharding

Single DB can't hold billions of rows efficiently. Shard by consistent hashing. Partition key carefully choose karo (user_id, entity_id).

High Write QPS (>5K) → Write Optimization

Async writes, message queues (Kafka), write-behind caching, batch inserts. Multiple write shards or CQRS pattern consider karo.

Peak QPS >50K → Horizontal Scaling

Load Balancer + multiple stateless app servers. Auto-scaling for peak. Rate limiting. Connection pooling. Stateless design mandatory.

Storage >10 TB → Distributed Storage

Object storage (S3) for blobs. Tiered storage (hot/warm/cold). Data partitioning + archival strategy. Compression helps.

Low Latency (<100ms) → In-Memory + CDN

Redis/Memcached for sub-ms reads. CDN for geo-distributed users. Pre-compute where possible. Denormalize data to avoid JOINs.
