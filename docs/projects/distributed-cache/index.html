Distributed Cache

Design a distributed caching system like Memcached or Redis Cluster. Multiple machines pe data cache karo, sub-millisecond latency do, aur lakhs of requests per second handle karo — while being fault-tolerant and horizontally scalable.

Requirements

step 1

✅ Functional Requirements

Core Operations:
→ PUT(key, value, ttl) — store with optional expiry
→ GET(key) — retrieve (sub-ms latency)
→ DELETE(key) — explicitly remove

Must Have:
→ Automatic eviction when memory full (LRU/LFU)
→ TTL-based expiration
→ Data distributed across multiple nodes
→ Automatic key routing to correct node

⚡ Non-Functional Requirements

Performance:
→ Read latency: <1ms (p99 <5ms)
→ Throughput: 100K+ ops/sec per node

Availability:
→ 99.99% uptime (4 nines)
→ No single point of failure

Scalability:
→ Horizontal scaling (add nodes = more capacity)
→ Linear throughput increase with nodes

📐 Rule of Thumb

Cache 20% of hot data (80/20 rule). Each Redis node ≈ 45GB usable → ceil(cache_size / 45GB) primary nodes. Double for replicas.

Consistent Hashing — The Core Idea

key concept

Problem: Simple hash(key) % N mein jab bhi node add/remove hota hai, almost ALL keys re-map ho jaate hain → cache stampede. Consistent hashing mein sirf K/N keys move hoti hain.

Virtual Nodes (Vnodes)

Problem: Real nodes pe data unevenly distribute hota hai. Solution: Har physical node ke 100-200 virtual nodes banao ring pe. Even distribution ensure hoti hai. Node add/remove pe load evenly spread hota hai.

Hash Function Choice

Use MurmurHash3 or xxHash — fast + uniform distribution. MD5/SHA overkill hain (cryptographic, slower). Har GET/PUT pe hash compute hota hai, so speed matters.

⚠️ Common Interview Mistake

"Consistent hashing" bol dete hain but explain nahi karte WHY simple modular hashing fails. Interviewer sunna chahta hai: "When N changes, hash % N remaps almost all keys → cache stampede. Consistent hashing limits remapping to K/N keys."

Eviction Policies

core design

Jab memory full ho jaaye toh kaunsa data hataayein? Wrong eviction = frequent cache misses = DB overloaded.

Policy Full Form How It Works Best For
LRU Least Recently Used Jo sabse lamba time se access nahi hua General purpose ✅
LFU Least Frequently Used Jo sabse kam baar access hua CDN, popular content
FIFO First In, First Out Jo pehle aaya, pehle hataao Simple, sessions
TTL Time To Live Expiry ke baad auto-delete Tokens, rate limits
Random Random Eviction Random item hataao Uniform access patterns
W-TinyLFU Window Tiny LFU LRU window + frequency sketch Best hit rate 🏆 (Caffeine)
✅ LRU Implementation — Interview Favorite

HashMap + Doubly Linked List. HashMap → O(1) lookup. DLL → access order (GET pe move to head, eviction pe remove tail). Result: O(1) GET, PUT, EVICT. Redis uses approximated LRU — samples random keys, evicts least recent from sample.

Cache Patterns — Read & Write Strategies

critical

Cache-Aside (Lazy Loading) ✅

Read: App → cache miss → DB → write cache
Write: App → DB → invalidate cache

✅ Simple, caches only needed data
❌ First request slow (miss)

Most common pattern 🏆

Read-Through

Read: App → cache (cache loads DB on miss)
Write: Same as cache-aside

✅ App code simpler
❌ Cache tightly coupled to DB

Cache manages DB loading

Write-Through

Write: App → cache → cache writes DB (sync)
Read: Always from cache (fresh)

✅ Cache always consistent
❌ Slower writes (2× write)

Strong consistency needed

Write-Behind (Write-Back)

Write: App → cache → async batch DB write
Read: Always from cache

✅ Fastest writes, DB batching
❌ Data loss risk on crash

Write-heavy workloads

Write-Around

Write: App → DB directly (skip cache)
Read: Cache-aside on read

✅ No cache pollution
❌ Recent writes = cache miss

Write-once, read-rarely

Refresh-Ahead

How: Async refresh before TTL expires
When: TTL <20% + recently accessed

✅ Zero miss for hot data
❌ Complex, wastes resources

Low-latency critical paths
🎯 Interview Mein Kya Bolo?

"For most cases → Cache-Aside (simple, caches on demand). Write-heavy → Write-Behind with durable queue. Strong consistency → Write-Through."

Deep Dive — Key Challenges

advanced
1

Cache Stampede / Thundering Herd

Problem: Popular key expires → 1000s of concurrent requests hit DB → DB crashes.

1. Locking (Mutex) First request gets lock → fetches DB → populates cache Others wait or get stale data Use: SET lock_key:user:42 1 NX EX 5 2. Early Expiration (Refresh-Ahead) TTL remaining < 20%? → background refresh before actual expiry 3. Never Expire + Background Update Cache never expires, background job updates periodically Stale data possible, but zero stampede
2

Hot Key Problem

Problem: Ek key (trending tweet) itna popular ki single node overwhelm ho jaaye.

1. Local Cache (L1) App server pe in-process cache (Guava/Caffeine) Hot keys locally cached → no network call → short TTL (5-10s) 2. Key Replication "celeb:123" → "celeb:123#1", "celeb:123#2", ... Client randomly picks suffix → load distributed across nodes 3. Read Replicas Hot node ke replicas banao → reads split
3

Cache Invalidation — "The Hard Problem"

Phil Karlton: "There are only two hard things in CS: cache invalidation and naming things."

1. TTL-based // simplest, good for 90% cases Set expiry. Data stale for max TTL duration. 2. Event-driven Invalidation // most accurate DB write → Kafka/CDC event → cache subscriber deletes key 3. Write-through Invalidation On DB write → immediately delete/update cache ⚠️ Race Condition: Thread A: READ cache (miss) → READ DB (old) Thread B: WRITE DB (new) → DELETE cache Thread A: SET cache (old) → STALE! Fix: Always "delete" not "update" on write + short TTL safety net
4

Large Value Handling

Problem: Values >1MB → network congestion, slow serialization, memory fragmentation.

→ Compress values (gzip/lz4) → 50-70% savings → Split into chunks: "key:part1", "key:part2" → Store pointer in cache, actual data in S3 → Set max value size limit (e.g. 512KB)

Replication & Fault Tolerance

reliability

Primary-Replica Model

Each primary → 1-2 replicas. Writes to primary → async replicate. On failure, replica promoted. This is Redis Cluster model.

Trade-off: Async replication = fast writes but small data loss window on failover.

Failure Detection

Gossip Protocol: Nodes periodically ping each other. No response → PFAIL. Majority agrees → FAIL → trigger failover.

Config Service: ZooKeeper/Etcd monitors health, triggers rebalancing.

Node Add/Remove

Add: New node gets hash slots. Data migrated live, slot by slot, zero downtime.

Remove: Slots redistributed to remaining nodes before shutdown. Consistent hashing → minimal data movement.
📌 Cache Is NOT Durable Storage

Cache is best-effort. Node dies, data lost — that's okay! Source of truth = database. Cache failure = increased latency (DB reads), not data loss. Design so system degrades gracefully without cache.

Redis vs Memcached

Redis

  • Rich data structures (lists, sets, sorted sets, hashes)
  • Persistence (RDB + AOF)
  • Pub/Sub, Lua scripting
  • Built-in clustering (Redis Cluster)
  • Single-threaded (no lock contention)
VS

Memcached

  • Simple key-value only
  • Multi-threaded (better CPU use)
  • Slightly faster for simple ops
  • Lower memory overhead per key
  • No persistence (pure cache)
🎯 Quick Answer

Redis → complex data structures (leaderboards, sessions, queues). Memcached → simple caching, max throughput. Default: Redis (more versatile).

Interview Questions & Answers

prep
❓ What happens when a cache node goes down?
Consistent hashing se sirf us node ki keys affected hoti hain (~1/N of total). Replica promote hota hai primary pe. Un keys ke requests temporarily DB pe jaate hain jab tak new node warm nahi ho jaata. Other nodes completely unaffected.
❓ How do you handle cache warming after restart?
1) Lazy: Requests naturally populate cache (simple, slow). 2) Pre-warm: Load hot-keys list from DB on startup. 3) Snapshot: Redis RDB restore. 4) Replica promotion: Already warm replica becomes primary.
❓ How to prevent cache penetration?
Cache penetration = queries for keys that will NEVER exist (invalid IDs). Every request misses → hits DB. Fix: 1) Cache null results with short TTL (~60s). 2) Bloom filter — O(1) check "definitely not in set" or "probably in set" → prevents unnecessary DB queries.
❓ How to implement distributed lock with cache?
Redis SET key value NX EX timeout. NX = atomic "set if not exists". EX = auto-expire (prevents deadlock). Distributed: Redlock — acquire lock on majority (N/2+1) Redis instances. Always set TTL to prevent permanent locks from crashed clients.
❓ How does Redis achieve high performance single-threaded?
I/O multiplexing (epoll/kqueue) — one thread handles thousands of connections. All in-memory (no disk I/O on reads). Optimized data structures (ziplist, skip list). No context switching, no locks. Redis 6+ uses I/O threads for network while keeping command execution single-threaded.
❓ When should you NOT use cache?
1) Write-heavy with low read reuse (constant invalidation). 2) Strongly consistent data (banking). 3) Data too large for memory. 4) Completely random access (no hot data, low hit rate). 5) System already fast enough — added complexity not worth it.
🔑 Interview Summary — Ye Zaroor Bolo

1. Core: Distributed in-memory KV store, sub-ms latency, 100K+ ops/sec per node.
2. Distribution: Consistent hashing + virtual nodes for even data spread.
3. Eviction: LRU (HashMap + DLL) with TTL expiration.
4. Pattern: Cache-Aside default. Write-Through for consistency.
5. Reliability: Primary-Replica, async replication, gossip failure detection.
6. Challenges: Stampede (locks), hot keys (L1 cache), invalidation (events + TTL).
7. Key insight: Cache is not durable — system must work without it, just slower.
