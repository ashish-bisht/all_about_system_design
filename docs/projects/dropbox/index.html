☁️ MEDIUM DIFFICULTY

Dropbox — File Storage & Sync

Upload, download, share and sync files across devices. Covers chunked uploads, S3 pre-signed URLs, conflict resolution, and permission models.

📋 REQUIREMENTS

Functional Requirements

+ What are the core functional requirements? Core
  • Upload — Users can upload files (few KB to 5GB) from any device
  • Download — Users can download files from any device
  • Share — Users can share files with others (public link or private with specific emails + access levels)
  • Sync — Files automatically sync across user's devices

Out of scope: File editing, in-browser preview, real-time collaboration

+ Why eventual consistency and not strong consistency? Trade-off

Strong consistency would mean every device sees the exact same file state at the exact same moment. This requires distributed locks and coordination — kills availability and performance.

For a file storage system, a few seconds delay in sync is perfectly acceptable. If you edit a file on laptop, seeing it on phone 2-5 seconds later is fine. Availability > Consistency here (AP in CAP theorem).

+ Why multipart upload with resume? Deep Dive

Imagine uploading a 4GB video. Without multipart:

  • Network drops at 3.5GB → start over from scratch
  • Single connection bottleneck → slow upload
  • Server memory overload holding entire file

With multipart (chunked) upload:

  • File split into chunks (e.g., 5-10MB each)
  • Each chunk uploaded independently
  • On failure, resume from last successful chunk
  • Parallel upload of chunks possible
  • Server never holds entire file in memory
+ Storage Estimation: Why object storage? Scale

Back of envelope:

  • 1 Billion users
  • Average 2GB per user
  • Total: ~2 Exabytes (2,000 Petabytes)

No traditional database or file system handles this. Object storage (S3) is the only option — it's designed for exactly this scale with 11 nines durability, automatic replication across AZs, and cost-effective tiered storage.

+ Why separate File Metadata and File Chunks? Deep Dive

Metadata (filename, type, owner, version) lives in Postgres — small, structured, queried often.

Actual file content lives in S3 as chunks. The Chunks table maps each piece to its S3 location.

This separation gives us:

  • Fast metadata queries without touching blob storage
  • Resume capability — we know exactly which chunks are uploaded
  • Deduplication — same chunk hash across files can point to same S3 object
  • Parallel download — client fetches multiple chunks simultaneously
+ Why separate Permissions from Share Links? Entity

Two different sharing models:

  • Permissions (Private) — Direct user-to-user sharing. "Share with ashish@gmail.com with read access." Query: "Show me all files shared with me" → SELECT * FROM permissions WHERE user_id = ?
  • Share Links (Public) — URL-based access. Anyone with the link can access. No auth check needed. The URL itself is the access token.

If we mixed them in one table, querying "files shared with me" would require scanning through all public links too — inefficient and messy.

🔌 API DESIGN

APIs

POST /files/upload-init
Initialize multipart upload. Returns pre-signed URL + upload session ID.
{
  // Request
  "filename": "vacation.mp4",
  "file_type": "video/mp4",
  "file_size": 2147483648,    // 2GB in bytes
  "total_chunks": 20
}

// Response 200
{
  "file_id": "f-abc123",
  "upload_id": "s3-upload-xyz",    // S3 multipart upload ID
  "presigned_url": "https://bucket.s3.../vacation.mp4?uploadId=xyz&...",
  "chunk_size": 104857600          // recommended 100MB chunks
}
+ Why POST for upload-init and not GET? API

We're creating a resource (upload session) and sending metadata in the body. GET requests with body are technically allowed but many clients and proxies ignore GET body. POST is the correct semantic choice here.

POST /files/{file_id}/upload-complete
Finalize upload after all chunks are uploaded to S3. Alternative: Use S3 event notification to trigger this automatically.
{
  // Request
  "upload_id": "s3-upload-xyz",
  "chunks": [
    { "chunk_number": 1, "etag": "abc123" },
    { "chunk_number": 2, "etag": "def456" }
  ]
}

// Response 200
{
  "file_id": "f-abc123",
  "status": "ready",
  "download_url": "/files/f-abc123/download"
}
+ Client callback vs S3 event notification — which to use? Trade-off

Option A: Client calls /upload-complete

  • Simple — client knows when it's done
  • Client sends chunk ETags for verification
  • Risk: client crashes before calling → orphaned upload

Option B: S3 Event → SNS/Lambda → Server

  • Server automatically knows when upload completes
  • No client dependency for finalization
  • Risk: notification fails/delays → user sees stale state

Best approach: Both! Client calls /upload-complete as primary. S3 events as backup/verification. A cron job cleans up orphaned uploads older than 24h.

GET /files/{file_id}/download
Get pre-signed download URL. Client downloads directly from S3. Supports parallel chunk download via byte-range requests.
// Response 200
{
  "file_id": "f-abc123",
  "filename": "vacation.mp4",
  "file_size": 2147483648,
  "download_url": "https://bucket.s3.../vacation.mp4?...",
  "expires_in": 3600,    // URL valid for 1 hour
  "chunks": [            // for parallel download
    { "chunk_number": 1, "byte_range": "0-104857599" },
    { "chunk_number": 2, "byte_range": "104857600-209715199" }
  ]
}
+ Why not serve files through our server? Deep Dive

Pre-signed URL → Direct S3 download because:

  • Server doesn't waste bandwidth streaming 5GB files
  • S3 CDN is optimized for high-throughput delivery
  • Server only handles metadata requests (lightweight)
  • Horizontal scaling is easier — server is stateless

Pre-signed URLs are time-limited (1hr) so security is maintained. Server's only job is: authenticate user → check permissions → generate URL → done.

GET /files/{file_id}/share
Get shareable URL for a file.
PUT /files/{file_id}/share
Update sharing permissions — set public/private, add/remove whitelisted emails with access levels.
{
  // Request
  "link_type": "private",
  "permissions": [
    { "email": "alice@example.com", "access": "read" },
    { "email": "bob@example.com", "access": "write" }
  ]
}

// Response 200
{
  "share_url": "https://dropbox.com/s/abc123xyz",
  "link_type": "private",
  "permissions": [...]
}
+ Public vs Private share links — what's the difference? Core

Public link: Anyone with the URL can access. No auth check. Server generates a unique, non-guessable URL (like a long random token). The URL itself IS the authorization.

Private link: Only whitelisted emails can access. When someone clicks the link, server checks: is this user's email in the permissions table? What access level? If not found → 403 Forbidden.

Key insight: Public share links should NOT be pre-signed S3 URLs because those expire (typically 1hr). Instead, share links are permanent server URLs that internally generate fresh pre-signed URLs on each access.

GET /files/sync?since={timestamp}
Get all file changes since last sync point. Used by client to detect remote changes.
// Response 200
{
  "changes": [
    {
      "file_id": "f-abc123",
      "action": "modified",
      "version": 3,
      "last_edited": "2025-02-10T14:30:00Z"
    },
    {
      "file_id": "f-def456",
      "action": "deleted",
      "version": 2,
      "last_edited": "2025-02-10T15:00:00Z"
    }
  ],
  "sync_cursor": "2025-02-10T15:00:00Z"
}
🔄 DATA FLOW

Upload Flow (Step by Step)

Client → POST /files/upload-init
Send metadata: filename, type, size, total_chunks. Server creates file record (status: "uploading"), calls S3 CreateMultipartUpload, returns file_id + upload_id + pre-signed URL.
Client → S3 Direct Upload (via SDK)
Client uses S3 SDK with pre-signed URL to upload chunks one by one (or in parallel). Each chunk gets an ETag from S3 on success. Client tracks progress locally.
On Failure → Resume from Last Chunk
If upload fails mid-way, client calls S3 ListParts with upload_id to see which chunks completed. Resumes from next incomplete chunk. No re-upload of successful chunks.
Client → POST /files/{file_id}/upload-complete
After all chunks uploaded, client sends list of {chunk_number, etag}. Server calls S3 CompleteMultipartUpload, updates file status to "ready", bumps version.
S3 Event Notification (Backup)
S3 triggers SNS/Lambda on upload completion as backup. If client crashed before calling upload-complete, this catches it. Cron job cleans orphaned uploads after 24h.

Download Flow

Client → GET /files/{file_id}/download
Server authenticates user, checks permissions, generates fresh pre-signed download URL from S3. Returns URL + file metadata + chunk byte-ranges.
Client → Direct S3 Download
Client uses pre-signed URL to download directly from S3. For large files, uses byte-range requests to download chunks in parallel across multiple connections.

Share Flow

Owner → PUT /files/{file_id}/share
Sets link_type (public/private). For private: adds emails with access levels to permissions table. Server generates unique, non-expiring share URL.
Recipient → Clicks Share Link
Public: No auth check, directly generate pre-signed S3 URL and serve. Private: Authenticate user → check permissions table → if allowed, generate pre-signed URL → serve. Else 403.

🔬 DEEP DIVES

Interview Deep Dives

+ How does file sync work across devices? Deep Dive

Two approaches:

1. Polling (Simple) — Client periodically calls GET /files/sync?since=timestamp to get changes. Works but wasteful — mostly empty responses.

2. Push (WebSocket / Long Polling) — Server pushes change notifications to connected devices. More efficient. When user edits file on laptop:

  • Upload completes → Server updates metadata (version++)
  • Server sends push notification to all user's connected devices
  • Phone receives notification → calls sync API → downloads updated file

Best approach: Hybrid — Use WebSocket for real-time push. Fall back to polling if WebSocket disconnects. Initial sync on app open always polls to catch up.

+ How to handle conflict resolution? Trade-off

Scenario: User edits file on laptop at 2:00 PM. Same user edits same file on phone at 2:01 PM (without syncing).

Strategy: First-write-wins + Conflict Copy

  • First upload that reaches server becomes the source of truth (version N+1)
  • Second upload detects version mismatch — server rejects the write
  • Server creates a "Conflicted Copy" of the second version
  • User sees both versions and manually decides which to keep or merge

This is exactly how Dropbox handles it in production — "Ashish's conflicted copy (Feb 10)" appears in the folder. Simple, predictable, no data loss.

Why not auto-merge? For binary files (videos, images), auto-merge is impossible. Even for text files, merge conflicts can corrupt data. Let the user decide — safest approach.

+ How to handle deduplication? Scale

With 1B users, many files will have identical content (same PDF shared multiple times, same meme, etc.). Storing duplicates wastes petabytes.

Content-addressable storage:

  • Each chunk is hashed (SHA-256) before upload
  • S3 key = hash of chunk content
  • Before uploading, check: does this hash already exist in S3?
  • If yes → just add a reference, skip upload entirely
  • If no → upload the chunk

Savings can be massive — Dropbox reported ~75% deduplication ratio in early days. That's 1.5 Exabytes saved on our 2EB estimate!

Trade-off: Deletion becomes tricky — need reference counting. Can't delete S3 object until ALL references are gone.

+ Why pre-signed URLs instead of streaming through server? Deep Dive

If server streams the file:

  • Server bandwidth = upload + download traffic (huge cost)
  • Server needs massive memory/CPU for streaming
  • Server becomes bottleneck — 1M concurrent downloads kills it
  • More servers needed just for bandwidth

With pre-signed URLs:

  • Server only handles metadata (tiny payload)
  • S3/CloudFront handles all bandwidth (built for this)
  • Server can be tiny and cheap — just auth + URL generation
  • Horizontal scaling is trivial — server is stateless

Security: Pre-signed URLs are time-limited (1hr typically) and specific to one object. Even if intercepted, they expire quickly.

+ What if S3 event notification fails? Trade-off

Problem: In the S3 notification approach, if notification is lost or delayed, the file shows as "uploading" forever in our DB even though it's complete in S3.

Solutions (defense in depth):

  • Primary: Client always calls /upload-complete explicitly
  • Secondary: S3 event notification as backup verification
  • Tertiary: Cron job runs every hour — finds files with status "uploading" older than 24h → checks S3 if multipart is complete → updates status or aborts
  • Client retry: If client doesn't get 200 from /upload-complete, it retries with exponential backoff

Key principle: Never rely on a single mechanism. Belt AND suspenders.

+ How would you scale the metadata database? Scale

1B users × average 50 files each = 50 billion rows in file metadata table. Single Postgres won't handle this.

Scaling strategy:

  • Read replicas — Since read:write is 100:1, add read replicas. Most queries (list my files, get metadata) go to replicas.
  • Sharding by user_id — Each shard holds a subset of users and ALL their files. Why user_id? Because most queries are "show me MY files" — single shard query, no scatter-gather.
  • Caching with Redis — Hot file metadata cached in Redis. Frequently accessed files (shared public links going viral) served from cache.
  • Separate permissions table — Can be sharded differently (by file_id) since access checks are per-file.
+ Sync Strategy — Why NOT WebSocket for everyone? Trade-off

The WebSocket temptation: "Just keep a persistent connection to every device for real-time sync!"

Reality check — do the math:

  • 500M devices connected simultaneously
  • Each WebSocket connection ≈ 50KB memory
  • Total: 500M × 50KB = 25TB memory just for connections
  • ~500 dedicated WebSocket servers needed

That's insane for just sending "hey, file changed" notifications.

Our approach — Lazy Sync:

  • App open: Poll GET /files/sync?since=timestamp to catch up on all missed changes
  • User clicks file: Quick version check → if mismatch, show "New version available, tap to download"
  • Mobile background: Use FCM (Android) / APNs (iOS) push notifications — OS already maintains persistent connection, piggyback on it
  • No persistent server connections needed — simple, cheap, effective

Interview tip: Show you considered WebSocket, explain why it doesn't scale, then propose the pragmatic solution. This shows maturity in system design thinking.

+ Optimal Chunk Size — Why 5-10MB and not 100MB? Deep Dive

Too small (1KB chunks):

  • 5GB file = 5 million chunks → 5M HTTP requests overhead
  • S3 multipart limit is 10,000 parts max
  • Metadata explosion in chunks table

Too large (100MB chunks):

  • Fail at 95MB → re-upload entire 100MB chunk
  • Slow connections: one chunk takes forever
  • Less parallelism opportunity (fewer chunks)
  • Resume granularity is poor

Sweet spot: 5-10MB

  • 5GB / 5MB = 1,000 chunks (well within S3's 10K limit)
  • Fail? Max 10MB re-upload — quick retry
  • S3 SDK uses 4-5 concurrent connections → excellent parallelism
  • Mobile-friendly size — works even on slower networks
  • Industry standard (S3 recommends 5-15MB for multipart)
+ CDN for viral files — when and why? Scale

Scenario: Someone shares a public Dropbox link on Twitter. 1M people click it in an hour.

Without CDN: All 1M requests hit S3 directly. S3 handles it (it's designed for scale) but:

  • Higher latency for users far from S3 region
  • S3 data transfer costs skyrocket
  • No edge caching benefits

With CDN (CloudFront/Cloudflare):

  • First request fetches from S3, cached at edge locations worldwide
  • Remaining 999,999 requests served from nearest edge — ultra-low latency
  • S3 egress cost drops ~90%
  • Geographic distribution — users in Tokyo get served from Tokyo edge, not US-East S3

When to CDN: Only for popular/public files. Private files with unique per-user pre-signed URLs won't benefit from CDN caching (each URL is different). Use CDN for: public share links, widely accessed company files, and any file with high read frequency.

+ Redis Cache — Why LFU eviction? Deep Dive

Problem: With 50 billion file metadata rows, we can't cache everything. Need smart eviction.

LRU (Least Recently Used): Evicts items not accessed recently. Problem: a one-time viral file access pattern can flush out genuinely hot items.

LFU (Least Frequently Used): Evicts items accessed least often overall. Better for Dropbox because:

  • Some files are accessed daily (team documents, shared folders) — these should stay cached
  • Random one-time accesses (someone shared a link once) shouldn't evict frequently used files
  • LFU naturally keeps "working set" files hot

Redis config: maxmemory-policy allkeys-lfu

What to cache: File metadata only (small). NOT file content (too large, S3/CDN handles that).

+ Master-Slave DB — Why async replication? Trade-off

Read:Write = 100:1 — overwhelming reads. Single DB can't handle it.

Master-Slave setup:

  • Master: Handles all writes (upload metadata, permission changes, version updates)
  • Slave(s): Handle reads (list files, get metadata, check permissions). Multiple replicas possible.

Why async (not sync) replication?

  • Sync replication: Master waits for slave to confirm write. If slave is slow/down, master blocks. Write latency increases. Availability drops.
  • Async replication: Master writes and immediately responds. Slave catches up in background. Few milliseconds lag.

Trade-off: With async, a user might upload a file and if they immediately check from another device hitting a slave, file might not appear for a few ms. Acceptable — eventual consistency is fine for file sync.

Indexing: Index on file_id for fast lookups, owner_id for "list my files" queries.

+ Common Interview Mistakes to Avoid Trade-off
  • ❌ Storing files in database — BLOBs in Postgres = disaster at scale. Always use object storage.
  • ❌ Streaming through server — Server becomes bandwidth bottleneck. Use pre-signed URLs for direct S3 access.
  • ❌ Single upload endpoint — Without multipart, large file uploads are fragile and slow.
  • ❌ Mixing public/private sharing in one table — Different access patterns need different data models.
  • ❌ Forgetting conflict resolution — Multi-device sync WILL have conflicts. Must have a strategy.
  • ❌ Strong consistency for sync — Overkill. Eventual consistency is perfectly fine for file sync.
  • ❌ No resume on upload failure — Without chunked upload + resume, a 5GB upload failure means starting over.
  • ❌ WebSocket for all users — 500M persistent connections = 25TB memory = 500 servers. Use lazy sync + FCM/APNs instead.
  • ❌ 100MB chunk size — Too large. Fail at 95MB = re-upload 100MB. Use 5-10MB for better retry granularity.
  • ❌ No CDN for popular files — Viral public links will hammer S3. CDN edge caching cuts latency and cost by 90%.
  • ❌ Single database — 50B rows needs master-slave with read replicas. Index on file_id and owner_id.
  • ❌ Over-engineering sync — Don't build real-time collaborative editing. Lazy version check on file open is simple, effective, and what Dropbox actually does.
