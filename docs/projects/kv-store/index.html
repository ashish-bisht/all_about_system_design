📋 Step 1

Requirements

Pehle scope lock karo — interview mein 2 minute mein ye clear hona chahiye.

✅ Functional Requirements

1. Users can SET key-value pairs
2. Users can GET value by key
3. Users can DELETE a key
4. Users can set TTL (expiration) on keys
5. When memory full, evict using LRU

⚡ Non-Functional Requirements

1. Low latency — sub-millisecond
2. High throughput — 100K+ ops/sec/node
3. Scalable — add nodes for more data
4. Available — 99.99% uptime
5. Fault tolerant — no data loss on crash

🚫 Out of Scope

— Complex data types (lists, sets, sorted sets)
— Persistence to disk (AOF/RDB)
— Pub/Sub messaging
— Transactions / Lua scripting
🎤 Interview Tip

Interviewer ko pehle scope confirm karo: "I'll focus on basic key-value operations with TTL and LRU. Complex data types are out of scope — should I include them?" Clarity dikhata hai.

🔬 Deep Dive 1

LRU Eviction — HashMap + Doubly Linked List

Sabse important — 100% interview mein puchha jaata hai.

🧠 Why HashMap + DLL?

O(1) for GET, SET, EVICT — single DS se nahi hoga.

OperationHashMapLinked ListHashMap + DLL
LookupO(1) ✅O(n) ❌O(1) ✅
Move to frontN/A ❌O(1) ✅O(1) ✅
Evict LRUO(n) ❌O(1) ✅O(1) ✅
 
// LRU Cache Core
class LRUCache:
    map:  HashMap<string, DLLNode>
    head: DLLNode  // most recent
    tail: DLLNode  // least recent → evict

    def get(key):
        if key not in map: return NULL
        node = map[key]
        if expired(node): _remove(node); return NULL
        _move_to_head(node)  // mark recently used
        return node.value

    def set(key, value, ttl=0):
        if key in map: update + _move_to_head
        else:
            if full: _evict_lru()  // remove tail
            _add_to_head(new node)

    def _evict_lru():
        victim = tail.prev
        _remove(victim); del map[victim.key]
❗ Thread Safety

Redis is single-threaded (no issue). Multi-threaded: use sharded locks for concurrency.

🔬 Deep Dive 2

TTL Expiration — Lazy + Active

🦥 Lazy Expiry

Check on access. Expired → delete + return NULL.

✅ Zero overhead

❌ Unused keys waste memory

⏰ Active Expiry

Every 100ms: sample 20 random keys, delete expired. If >25% expired, repeat.

✅ Reclaims memory

❌ CPU overhead

🏆 Hybrid (Redis)

Lazy + Active combined. Probabilistically complete. Best approach.

✅ RECOMMENDED
🔬 Deep Dive 3

Consistent Hashing

Keys evenly distribute + min disruption on node change.

❌ hash(key) % N Fails

// N=3 → N=4: ~75% keys remap → stampede!
hash("user:1") % 3 = 2 → Node C
hash("user:1") % 4 = 1 → Node B  ← CHANGED!

✅ Hash Ring + Virtual Nodes

Nodes placed on ring. Key hashed → walk clockwise → first node = owner. Node dies? Only K/N keys remap. Virtual nodes (150/physical) ensure even distribution.

for i in range(150):
    ring[hash(f"NodeA-{i}")] = "NodeA"
⚠️ Interview Mistake

Don't just say "consistent hashing." Explain WHY simple hash%N fails: "When N changes, almost all keys remap → cache stampede."

🔬 Deep Dive 4

Replication & Fault Tolerance

1

Primary-Replica Model

Writes → primary. Reads → primary or replica. Async replication (fast, acceptable data loss for cache). Primary crash → replica promotes.

2

Gossip Protocol

Every 1s: ping 3 random nodes. No response 5s → SUSPECT. 3+ agree → FAILED → promote replica → update ring.

🎤

Why async?

"Cache ≠ source of truth. Sub-ms latency > durability. Need strong consistency? Use DB directly."

🔬 Deep Dive 5

Cache Stampede & Hot Keys

1

Cache Stampede

Problem: Popular key expires → 1000s miss → DB crash.

1. Mutex: First req locks → fetches DB → populates. Others wait.
2. Refresh-Ahead: TTL < 20%? Background refresh before expiry.
3. Stale-While-Revalidate: Return stale + async refresh.
2

Hot Key Problem

Problem: One key 100x traffic → single node bottleneck.

1. L1 Local Cache: App-local (100 items, 30s TTL). Zero network.
2. Key Replication: "product:42:random(1,5)" — 5 copies.
3. Read Replicas: Route hot key reads to replicas.
🔑 Production: Combine All

L1 local (ultra-hot) + distributed (all) + mutex (prevent stampede) + refresh-ahead (prevent gaps).

❓ Top Interview Questions

Q1

"Cache kab use karein?"

Use: Read-heavy, can be stale, repeated access. Don't: Write-heavy, strong consistency, one-time data.

Q2

"Cache-Aside vs Read/Write-Through?"

Cache-Aside: App checks cache → miss → DB → populate. Most common. Read-Through: Cache fetches DB. Write-Through: Sync write to both.

Q3

"Redis vs Memcached?"

Redis: Rich types, persistence, single-threaded. Memcached: Pure KV, multi-threaded, simpler. Pick Redis.

Q4

"Cache invalidation?"

TTL (safety net) + event-driven (fast). Write-through for strong consistency.

Q5

"Node dies?"

Gossip detects → promote replica → update ring → temp DB load during transition.
