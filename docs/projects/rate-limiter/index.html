🛡️ Project 03 — Easy

Rate Limiter

Design a distributed rate limiting system that protects APIs from abuse while ensuring fair usage. Used by every major API platform — Stripe, Twitter, Cloudflare, AWS.

📁 Difficulty: Easy
⏱️ Interview: 30–40 min
🔥 Frequency: Very High
🏷️ Category: Infrastructure
🛡️ Dealing with Contention 📖 Scaling Reads ✍️ Scaling Writes ⚡ Low Latency 🔄 Distributed Systems

🎯 Step 1

Requirements

Clarify functional and non-functional requirements upfront.

✅ Functional Requirements

FR-1: Client Identification

Identify clients by User ID, IP Address, or API Key with priority-based resolution: User ID → API Key → IP.

FR-2: Configurable Rate Rules

Limit HTTP requests based on configurable rules — e.g., 1000 req/min for authenticated users, 50 req/min for anonymous IPs.

FR-3: Meaningful Rejection

Return HTTP 429 Too Many Requests with rate limit headers when limits are exceeded.

⚡ Non-Functional Requirements

NFR-1: Low Latency

Rate check must be < 5ms — it runs on every single request as middleware.

NFR-2: Scalable

Handle millions of concurrent users across multiple API gateway instances.

NFR-3: Fault Tolerant

If rate limiter is down, system should fail open — allow requests rather than blocking legitimate traffic.

💡 Interview Tip

Always ask: "Should the rate limiter be at the application level or infrastructure level?" — It shows you understand the placement matters.

🧩 Step 2

Core Entities

Three core entities power the rate limiting system.

📦 Entity Model

EntityDescriptionFields
Client Who is making the request Identified by: user_id, api_key, or ip_address (priority order)
Rule What limits apply max_requests, window_seconds, identifier_type, endpoint (optional)
Counter Current request count in window identifier_key, request_timestamps, window_start

🔑 Client Identification Priority

Different trust levels get different rate limits:

if "Authorization" in headers → extract user_id → 1000 req/min  (highest trust)
elif "X-API-Key" in headers   → extract api_key → 500 req/min   (registered dev)
elif request.client.host      → use IP address  → 50 req/min    (anonymous)
else                          → REJECT immediately               (no identity)
⚠️ Why priority-based?

A logged-in user should get their full limit regardless of IP changes (mobile → wifi). API key users are registered and somewhat trusted. IP-only gets lowest limit as anyone could be behind that IP.

🗝️ Redis Key Design

Each identifier maps to a unique Redis key with type prefix to avoid collisions:

rate_limit:user:<hash(user_id)>      → Authenticated user counter
rate_limit:apikey:<hash(api_key)>    → API key counter
rate_limit:ip:<hash(ip_address)>     → IP-based counter

# Examples:
rate_limit:user:a1b2c3d4      → Ashish's counter (1000/min limit)
rate_limit:apikey:x7y8z9      → Dev app counter (500/min limit)
rate_limit:ip:f5e6d7c8        → Anonymous counter (50/min limit)
💡

Why hash the identifier?

IPv6 addresses contain colons (2001:0db8::1) which conflict with Redis key separators. Hashing gives consistent, fixed-length keys regardless of identifier type.

🧮 Step 3

Algorithms Deep Dive

Four major algorithms — each with different trade-offs.

🪣 Token Bucket

Bucket holds tokens (capacity = limit). Each request consumes 1 token. Tokens refill at fixed rate. Empty bucket = rejected.

✅ Allows burst traffic — bucket full? Fire all at once!

Used by: AWS, Stripe, API Gateway

Great for APIs

🚿 Leaky Bucket

Requests enter a queue (bucket). Queue processes at fixed rate. Queue full = rejected. Output is always smooth.

⚠️ No burst — constant output rate regardless of input.

Used by: Nginx, traffic shaping

Smooth output

🪟 Fixed Window Counter

Divide time into fixed windows (e.g., per minute). Count requests in current window. Count ≥ limit = rejected. Window ends = counter resets.

❌ Boundary burst problem — 2x limit possible at window edges!

Used by: Simple internal tools

Simple but flawed

📐 Sliding Window

Combines sliding log + counter. Looks at weighted count across current and previous window. No boundary issues. Accurate limiting.

✅ Most accurate — no boundary burst, smooth limiting.

Used by: Cloudflare, Redis-based systems

✅ Our Choice

🏠 Real-Life Analogies

Token Bucket = Jio Recharge

2GB/day limit — but you CAN download 2GB all at once in morning (burst). Phir slowly recharge hoga next day.

Leaky Bucket = Office WiFi with Speed Limit

Always 27 KB/sec max — chahe free ho ya urgent download. Constant speed, no burst.

Fixed Window = Club Bouncer (Hourly Reset)

Max 10 people per hour. 8:59 PM pe 10 aaye, 9:01 pe 10 aur — 20 in 2 minutes! 😱

Sliding Window = Smart Bouncer

"Last 60 minutes mein kitne aaye?" — no fixed boundary, always accurate count.

🎯

When to use what?

Token Bucket — Video streaming, file downloads, bursty APIs. Sliding Window — Payment APIs, auth endpoints, general API gateway. Leaky Bucket — Message queues, smooth traffic shaping. Fixed Window — Avoid in production, okay for internal tooling.

🏗️ Step 4

High-Level Design

Rate Limiter sits as middleware in the API Gateway — before requests reach backend servers.

System Architecture

✅ Key Design Decision: API Gateway Middleware

Rate limiter sits BEFORE the application server — requests are checked and rejected at the gateway level itself. This protects backend from unnecessary load.

🛠️ Step 5

API / Interface

Rate Limiter is middleware, not a separate endpoint. It adds headers to every response.

📤 Response Headers (Every Response)

# Success (200, 201, etc.)
X-RateLimit-Limit: 1000           # Total limit for this window
X-RateLimit-Remaining: 847        # Requests remaining
X-RateLimit-Reset: 1707234567     # Unix timestamp when window resets

# Rate Limited (429)
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1707234567
Retry-After: 30                    # Seconds to wait before retrying

⚙️ Internal Function Interface

async def rate_limit_check(
    identifier: str,        # "user:a1b2c3" or "apikey:x7y8z9" or "ip:f5e6d7"
    limit: int,             # Max requests allowed (e.g., 1000)
    window_seconds: int     # Time window (e.g., 60)
) -> RateLimitResult:
    """
    Returns:
        allowed: bool       # True = proceed, False = reject
        remaining: int      # Requests left in window
        reset_at: int       # Unix timestamp when window resets
    """

🔀 Middleware Flow (Pseudocode)

@app.middleware("http")
async def rate_limiter_middleware(request, call_next):
    # Step 1: Extract identifier (priority-based)
    identifier = extract_identifier(request)
    if not identifier:
        return Response(status=403, body="No valid identifier")

    # Step 2: Determine limit based on identifier type
    limit = get_limit_for_type(identifier.type)
    # user → 1000/min, apikey → 500/min, ip → 50/min

    # Step 3: Check rate limit (Redis Lua script)
    result = await rate_limit_check(identifier.key, limit, window=60)

    # Step 4: Reject or proceed
    if not result.allowed:
        return Response(
            status=429,
            headers={
                "X-RateLimit-Limit": str(limit),
                "X-RateLimit-Remaining": "0",
                "X-RateLimit-Reset": str(result.reset_at),
                "Retry-After": str(result.retry_after)
            }
        )

    # Step 5: Proceed + attach headers
    response = await call_next(request)
    response.headers["X-RateLimit-Limit"] = str(limit)
    response.headers["X-RateLimit-Remaining"] = str(result.remaining)
    response.headers["X-RateLimit-Reset"] = str(result.reset_at)
    return response

Data Flow

Step-by-step flow of a request through the rate limiter.

Request Flow — Sliding Window

💾 Deep Dive 1

Redis Implementation

Sliding Window using Redis Sorted Sets — the production-grade approach.

📊 How Sliding Window Works in Redis

Each request's timestamp is stored in a Redis Sorted Set. The score AND member are both the timestamp.

# User ashish makes requests at these times:
# Limit: 5 requests per 60 seconds

t=100 → ZADD rate_limit:user:abc 100 100  → Set: {100}           → count=1 ✅
t=115 → ZADD rate_limit:user:abc 115 115  → Set: {100,115}       → count=2 ✅
t=130 → ZADD rate_limit:user:abc 130 130  → Set: {100,115,130}   → count=3 ✅
t=145 → ZADD rate_limit:user:abc 145 145  → Set: {...,145}       → count=4 ✅
t=150 → ZADD rate_limit:user:abc 150 150  → Set: {...,150}       → count=5 ✅

t=155 → window_start = 155-60 = 95
         ZREMRANGEBYSCORE ... 0 95 → nothing removed (all > 95)
         ZCARD → 5 → 5 >= 5 → ❌ REJECTED!

t=165 → window_start = 165-60 = 105
         ZREMRANGEBYSCORE ... 0 105 → removes t=100!
         ZCARD → 4 → 4 < 5 → ✅ ALLOWED! → ZADD 165

🔒 Atomic Lua Script

All three operations in ONE atomic call — no race conditions possible.

-- rate_limiter.lua
local key = KEYS[1]                    -- rate_limit:user:abc123
local window = tonumber(ARGV[1])       -- 60 (seconds)
local limit = tonumber(ARGV[2])        -- 1000
local now = tonumber(ARGV[3])          -- current timestamp (ms)
local window_start = now - (window * 1000)

-- Step 1: Remove expired entries (outside window)
redis.call('ZREMRANGEBYSCORE', key, 0, window_start)

-- Step 2: Count current entries
local count = redis.call('ZCARD', key)

-- Step 3: Check limit
if count < limit then
    -- ALLOWED: Add new entry + set TTL
    redis.call('ZADD', key, now, now)
    redis.call('PEXPIRE', key, window * 1000)
    return {1, limit - count - 1, now + (window * 1000)}
    --     allowed, remaining,    reset_at
else
    -- DENIED: Don't add, return info
    local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
    local reset_at = tonumber(oldest[2]) + (window * 1000)
    return {0, 0, reset_at}
    --     denied, remaining=0, reset_at
end
✅ Why Lua Script?

Redis executes Lua scripts atomically — no other command can run in between. This eliminates race conditions between ZCARD (check) and ZADD (update) that would allow limit bypass.

⚡ Deep Dive 2

Race Conditions

Why atomicity matters in distributed rate limiting.

🐛 The Race Condition Bug

Without atomic operations, two gateway instances can bypass limits simultaneously:

# User: ashish | Limit: 5/min | Current count: 4

Gateway 1 (Request A):              Gateway 2 (Request B):
─────────────────────               ─────────────────────
ZCARD → count = 4 ✅                ZCARD → count = 4 ✅
4 < 5 → ALLOW!                      4 < 5 → ALLOW!
ZADD  → count = 5                   ZADD  → count = 6 😱

# Both allowed! Limit was 5 but 6 requests got through!

✅ The Fix: Atomic Lua Script

# Same scenario with Lua Script:

Gateway 1 (Request A):              Gateway 2 (Request B):
─────────────────────               ─────────────────────
LUA SCRIPT START 🔒
  ZCARD → 4                         ⏳ WAITING (Redis locked)
  4 < 5 → ALLOW                     ⏳ WAITING...
  ZADD → count = 5
LUA SCRIPT END 🔓
                                     LUA SCRIPT START 🔒
                                       ZCARD → 5
                                       5 >= 5 → DENIED ❌
                                     LUA SCRIPT END 🔓

# Correct! Only 5 requests allowed. Gateway 2 properly rejected.
🏠

Analogy: Bathroom Lock

Without Lua = bathroom door open, 2 people walk in simultaneously 😅. With Lua = door locked, one waits outside until the other finishes 🔒.

🛡️ Deep Dive 3

Fault Tolerance

What happens when Redis goes down? The answer determines your system's philosophy.

🔥 Fail Open vs Fail Closed

StrategyBehaviorRiskWhen to Use
Fail Open ✅ Allow all requests Temporary abuse possible API Gateway (availability > protection)
Fail Closed Block all requests Legitimate users blocked! Payment/Security critical systems
⚠️ Our Choice: Fail Open

Service being down is worse than temporary lack of rate limiting. Legitimate users getting blocked = revenue loss. Brief abuse window is recoverable.

🔄 Multi-Layer Fallback Strategy

async def rate_limit_check(identifier, limit, window):
    try:
        # Layer 1: Redis Cluster (primary)
        return await redis_cluster.eval(lua_script, key, args)
    except RedisClusterError:
        try:
            # Layer 2: Local in-memory counter (approximate)
            return local_counter.check(identifier, limit, window)
        except Exception:
            # Layer 3: Fail Open — allow everything
            log.warning("Rate limiter fully down, failing open")
            return RateLimitResult(allowed=True, remaining=limit)

Layer 1: Redis Cluster — distributed, accurate, fast.
Layer 2: Local counters per gateway instance — not shared, but better than nothing.
Layer 3: Fail open — allow all requests, log for monitoring.

🔄 Deep Dive 4

Consistent Hashing

How to distribute rate limit keys across Redis Cluster nodes with minimal disruption.

❌ Problem: Simple Hash Modulo

# 3 Redis nodes: R1, R2, R3
hash("rate_limit:user:ashish") % 3 = 1  → R2 ✅

# Add R4 (scaling up):
hash("rate_limit:user:ashish") % 4 = 3  → R4 😱
# Key moved! Counter lost! User's limit temporarily reset!

Adding/removing nodes reshuffles ALL keys — every user's counter resets!

✅ Solution: Consistent Hashing Ring

# Nodes placed on hash ring:
Ring: [0 ... R1(100) ... R2(300) ... R3(600) ... 2^32]

hash("rate_limit:user:ashish") = 250 → nearest node clockwise = R2 ✅

# Add R4 at position 450:
Ring: [0 ... R1(100) ... R2(300) ... R4(450) ... R3(600) ...]

hash("rate_limit:user:ashish") = 250 → still R2 ✅ (no change!)
# Only keys between 300-450 move to R4 (~1/N keys affected)

🔑 How It Works for Rate Limiting

# Every request:
identifier = "rate_limit:user:hash(ashish)"

# Consistent hash determines which Redis node
node = consistent_hash(identifier)  → R2

# Lua script runs on THAT specific node
result = R2.eval(lua_script, identifier, [window, limit, now])

# Same identifier ALWAYS goes to same node
# = consistent counter, no double-counting
💡

Key Point for Interview

Consistent hashing works on the Redis key string — it doesn't care if it's a user_id, api_key, or IP. Any string gets hashed to a position on the ring, routed to the nearest node. Simple and uniform.

Interview Tips & Cheatsheet

Quick reference for the interview room.

🏆 30-Second Elevator Pitch

"I'd design the rate limiter as middleware in the API Gateway layer.
Client identification uses a priority system — user_id > api_key > ip.

For the algorithm, I'd use Sliding Window with Redis Sorted Sets
because it's accurate (no boundary burst) and Redis-native.

All operations happen in an atomic Lua script to prevent race
conditions across multiple gateway instances.

For scaling, Redis Cluster with consistent hashing distributes
keys evenly. Fault tolerance uses fail-open with local counters
as fallback."

🔥 Common Follow-up Questions

Q: "Why not Token Bucket?"

"Token Bucket is great when you WANT burst — like video streaming or file downloads. For a general API gateway where we want fair, consistent limiting, Sliding Window is more accurate."

Q: "What if someone changes IP to bypass?"

"That's why we have priority-based identification. Authenticated users are tracked by user_id regardless of IP. Only anonymous users fall back to IP-based limiting with the lowest limits."

Q: "How do you handle distributed rate limiting across data centers?"

"Two approaches: (1) Global Redis Cluster with cross-DC replication — accurate but higher latency. (2) Local rate limiting per DC with slightly higher total limits — faster but less precise. Choice depends on consistency requirements."

Q: "What about per-endpoint rate limits?"

"Extend the Redis key: rate_limit:user:abc:POST:/api/payment. Different endpoints get different rules — payment APIs get stricter limits than read APIs."

Q: "How do you monitor rate limiting?"

"Emit metrics on every check: total requests, allowed, denied, latency. Dashboard shows denial rate per user type. Alerts on sudden spikes in 429s or Redis latency."
